# SEO-аудит `/watch` и индексации (Weeb-X)

Дата: 2026-10-06. Ветка: `arena/857be0e3-anime-host-anix1`.

Вопрос был: «проверить полностью SEO для `/watch` и её индексацию, потому что тайтл
не находится по поисковым запросам».

Короткий ответ: **технически страница `/watch` сделана хорошо, но сайт сам
не давал поисковикам найти свои тайтлы.** Плюс было несколько дефектов
микроразметки, из-за которых расширенные сниппеты не могли появиться в принципе.

Всё, что ниже, проверено не на глаз: приложение собиралось прод-сборкой,
поднимался локальный сервер, страницы запрашивались `curl`, JSON-LD парсился,
XML карты сайта валидировался. Дополнительно сверялись живые `robots.txt`
и `sitemap.xml` продакшена.

---

## 1. Что было главной причиной («тайтла нет в поиске»)

### 1.1. В карте сайта было ~200 страниц `/watch` из десятков тысяч возможных

`app/sitemap.ts` собирал ссылки только из четырёх «витринных» списков Shikimori
по 50 позиций:

| Источник | Что реально давал |
|---|---|
| `getPopularNow(50)` | 50 онгоингов по популярности |
| `getPopularAlways(50)` | 50 вышедших с оценкой ≥ 8 |
| `getOngoingList(50)` | 50 онгоингов по рейтингу (сильно пересекается с первым) |
| `getTopOfWeek(50)` | **тот же список, что `getPopularNow`** — 0 новых URL |
| `getAnnouncements(50)` | 50 анонсов |

`getTopOfWeek` буквально реализован как `return getPopularNow(limit)`, а
`shikimoriJson` кэширует по URL запроса — то есть это была та же самая выборка.
В логе сборки это видно как два одинаковых запроса
`GET /api/animes?limit=50&order=popularity&status=ongoing&score=7`.

Итог — в карте сайта оказывалось ~150–200 уникальных страниц `/watch`.

**Исправлено:** добавлен постраничный добор каталога
(`getCatalogPage(page)`, по 50 тайтлов на страницу), дубликат `getTopOfWeek`
убран. Количество страниц регулируется переменной окружения
`SITEMAP_CATALOG_PAGES` (по умолчанию 40 страниц = 2000 тайтлов).

### 1.2. `/catalog` не содержал в HTML ни одной ссылки на тайтл

Это была вторая половина проблемы. Обход сайта поисковиками идёт по ссылкам,
и главный «хаб» каталога ссылок не отдавал вообще:

- `app/catalog/page.tsx` рендерил `CatalogPageWrapper` → `CatalogClient`;
- `CatalogClient` — клиентский компонент, начинавшийся с `useState<Anime[]>([])`
  и `loading = true`, а данные тянул через **server action** уже после гидратации;
- Googlebot server action не вызывает → в HTML `/catalog` было **0** ссылок
  вида `/watch/...` (проверено: `grep -o 'href="/watch/[^"]*"' | wc -l` → `0`).

Единственными путями обхода оставались главная страница (~30 карточек)
и карта сайта (~200 адресов). Пагинация при этом закрыта в `robots.txt`
(`Disallow: /*?page=`), то есть дальше первой страницы каталога робот не уйдёт.

**Исправлено:** первая страница каталога теперь запрашивается на сервере
(`getAnimeCatalog(initialFilters)` в `app/catalog/page.tsx`) и передаётся
в клиент как `initialAnimes`. Ссылки попадают в HTML сразу, а повторный
запрос из браузера не делается (`skipFirstFetch`).

Проверка после правки: `/catalog` отдаёт **24** уникальные ссылки на `/watch/*`
в серверном HTML.

### 1.3. `robots.txt` запрещал обход CSS и JS

```
Disallow: /_next/
```

Это закрывает `/_next/static` (стили и бандлы) и `/_next/image`
(оптимизированные картинки). Google прямо просит так не делать: без CSS/JS
он не может отрендерить страницу, оценить mobile-friendly и подтянуть
изображения — страдает и индексация, и ранжирование.

**Исправлено:** строка удалена.

### 1.4. `/watch/[id]` не кэшируется вообще

В прод-сборке страница отдаётся с заголовком:

```
Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate
```

(`/watch/[id]` в отчёте сборки помечен как `ƒ Dynamic`). Причины две:
`getEditorialReview` ходит в Supabase с `cache: 'no-store'`, а сама страница
читает `searchParams` (`?episode=`), что в Next 15 тоже форсирует динамический
рендер.

Что это значит: каждая страница на каждый визит и на каждый заход робота
рендерится заново, с живыми запросами к Shikimori (`getAnimeById` +
`getAnimeFranchise`, а тот делает по запросу на каждый узел франшизы — для
«Наруто» или «Детектива Конана» это десятки вызовов). CDN не может закэшировать
ничего. Это бьёт по TTFB, по Core Web Vitals и по скорости обхода: робот
успевает обойти меньше страниц за тот же бюджет.

**Рекомендация (не делал, нужна аккуратная переработка):** вынести серию из
`searchParams` в сегмент маршрута (`/watch/[id]/[episode]`) либо отказаться от
посезонного `title`/`description`, чтобы страница стала ISR (`export const
revalidate = 3600`), а `getEditorialReview` переключить с `cache: 'no-store'`
на `next: { revalidate: N }` плюс точечная ревалидация при правке отзыва.

## 2. Дефекты микроразметки (почему не было расширенных сниппетов)

### 2.1. `alternateName` содержал только русское название

`transformAnime` формировал объект без полей `russian`, `english`, `japanese`,
`kind`, а `app/watch/[id]/page.tsx` объявлял их через `type ExtendedAnime = Anime & {...}`
и читал как будто они есть. В результате `anime.english` и `anime.japanese`
были `undefined`.

Было (реальный JSON-LD со страницы «Атака титанов»):

```json
"alternateName": ["Атака титанов"]
```

То есть по запросам латиницей («attack on titan», «shingeki no kyojin»)
разметка не давала поисковику ни одной подсказки, и ключевые слова
`altTitle` в мета-теге тоже не заполнялись.

**Исправлено:** `transformAnime` прокидывает `english`, `japanese`, `kind`,
`shikimoriRating`, `isNsfw`; тип `ExtendedAnime` убран как избыточный.

Стало:

```json
"alternateName": ["Attack on Titan", "進撃の巨人", "Атака титанов"]
```

### 2.2. `@type` всегда был `TVSeries`, даже для фильмов

Следствие того же бага: `anime.kind` был `undefined`, поэтому условие
`anime.kind === "movie" ? "Movie" : "TVSeries"` всегда давало второе.

**Исправлено и проверено:** для фильма теперь `"@type": "Movie"`.

### 2.3. Выдуманный `aggregateRating` — прямой риск санкций

```js
const deterministicRatingCount = 80 + (Number.parseInt(cleanId, 10) % 120)
jsonLd["aggregateRating"] = { ratingValue: animeRating, ratingCount: deterministicRatingCount, ... }
```

Здесь две проблемы сразу:

1. `ratingCount` не существовал — число вычислялось из ID тайтла;
2. `ratingValue` брался из Shikimori, то есть это оценка **чужой** площадки,
   а не пользователей weeb-x.com.

Правила Google требуют, чтобы оценки были настоящими и принадлежали вашему
сайту. За такое выдают ручные санкции на «спамную разметку» — а они гасят
**все** расширенные сниппеты домена, а не только на странице-нарушителе.

**Исправлено:** блок удалён. В коде оставлен комментарий, что возвращать его
можно только со реальным счётчиком оценок из своей БД.

### 2.4. `VideoObject.embedUrl` вёл на гарантированный 404

В разметке было:

```json
"embedUrl": "https://weeb-x.com/embed/16498"
```

Но `/embed/[token]` — это не id, а **AES-256-GCM-токен с истечением срока**
(`resolvePlayerToken` в `lib/player-protect.ts`). Обычный `16498` токеном не
является, поэтому такой адрес не открывается ни у кого — ни у браузера, ни у
робота. Вдобавок сам роут отдаёт `notFound()` для известных краулеров
(`isCrawlerRequest`), закрыт в `robots.txt` (`Disallow: /embed/`) и помечен
`X-Robots-Tag: noindex, nofollow, noarchive`.

То есть Google получал ссылку на плеер, которая для него всегда 404, — по
правилам видеоразметка с неработающим `embedUrl` не проходит валидацию,
и видео-сниппеты не показывались.

**Исправлено:** `embedUrl` убран (плеер и так находится на самой странице,
`contentUrl` на неё указывает). Заодно убран захардкоженный `"duration": "PT24M"`,
который для полнометражек просто неверен.

### 2.5. Хентай/18+ определялся... никак

`isHentaiContent` сравнивал `anime.rating` со списком `['rx', 'r+', 'r18', '18+']`,
но в `Anime` поле `rating` — это **число** (`parseFloat(item.score)`), а не
строковый рейтинг. Строковый рейтинг Shikimori выбрасывался в `transformAnime`,
хотя в `types.ts` он подписан как «Важно для фильтрации хентая». Жанры
Shikimori для NSFW-тайтлов неавторизованному клиенту не отдаёт, поэтому и
проверка по жанрам почти никогда не срабатывала.

Последствия: 18+ страницы индексировались как обычные. Это не только
репутационная история — массовая индексация adult-контента на домене роняет
весь сайт в SafeSearch и мешает ранжированию обычных тайтлов.

**Исправлено:** `transformAnime` прокидывает `shikimoriRating` и `isNsfw`
(через существующий `isAnimeSafe`), детектор переписан на эти поля,
страницы с NSFW получают `robots: noindex, follow`, а из карты сайта такие
тайтлы исключены.

Проверено: обычный тайтл → `index, follow, max-video-preview:-1, ...`;
NSFW-тайтл → `noindex, follow`.

Заодно `isAnimeSafe` защищён от жанра без `russian`/`name` — иначе один битый
жанр в ответе Shikimori ронял бы всю страницу, так как функция теперь
вызывается из `transformAnime` на каждом тайтле.

## 3. Мягкие 404 из-за `app/loading.tsx`

`/watch/999999` (несуществующий тайтл) отдавал **HTTP 200** с
`<meta name="robots" content="noindex">`. В Search Console такие адреса
собираются как «Мягкая 404» и тратят краулинговый бюджет.

Причина архитектурная и описана ещё в комментариях к middleware: корневой
`app/loading.tsx` оборачивает все страницы в Suspense, заголовки уходят
со статусом 200 раньше, чем в `page.tsx` вызовется `notFound()` — статус
после этого уже не поменять.

**Исправлено:** решение вынесено в middleware, до рендера. Добавлена функция
`doesWatchAnimeExist()`, которая возвращает `true` / `false` (Shikimori уверенно
ответил 404, ответ кэшируется на 10 минут) / `null` (сеть или 429 — страницу
не блокируем). При `false` middleware отдаёт настоящий 404.

Проверено: `/watch/999999` → **404**, существующий тайтл → **200**.
Задержки для живых страниц нет: вердикт берётся из уже существующего кэша
сегментов, при промахе обход уходит в фон (`event.waitUntil`).

## 4. Что ещё стоит решить (не менял, нужен ваш выбор)

### 4.1. `?episode=N`: противоречивые сигналы

`robots.txt` говорит Яндексу `Clean-param: episode /watch` — то есть «считай
`?episode=2` тем же адресом». А страница отдаёт self-canonical
`/watch/…-slug?episode=2` и `index, follow`. Получается: Google видит N
индексируемых почти одинаковых страниц на один сериал, Яндекс — одну.

Нужно выбрать одну стратегию:

- **оставить посерийные страницы** (у них разные `title`/`description`,
  это высокочастотные запросы «X серия смотреть онлайн») — тогда убрать
  `Clean-param: episode /watch`;
- **схлопнуть в один адрес** — тогда canonical серии должен указывать на
  адрес без параметра.

Рекомендую первый вариант: посерийные заголовки — это как раз то, по чему
люди ищут, и сейчас они работают.

### 4.2. Каноникал каталога игнорирует фильтры

`app/catalog/page.tsx` жёстко возвращает `canonical: "https://weeb-x.com/catalog"`
для всех фильтров, при этом отдаёт `robots: index, follow` (в коде так и
написано: «Разрешаем индексировать страницы фильтров»). Получается, что
страницы «аниме 2024 года», «аниме в жанре Экшен» и т. п. индексируются,
но указывают каноническим на общий `/catalog` — и выпадают из индекса сами
себя. Либо делайте каноникал с параметрами (это неплохой трафик по
низкочастотке), либо ставьте `noindex` на фильтровые комбинации.

### 4.3. `duration` в `VideoObject`

Захардкоженный `PT24M` убран, но и настоящей длительности нет. Если хотите
видео-сниппеты — её нужно брать из API плеера.

### 4.4. `og:image` и прокси картинок

- В `openGraph` указан `width: 1200, height: 630`, но постер — вертикальный
  (~3:4). Соцсети обрежут его; лучше отдавать отдельную OG-картинку 1200×630.
- В JSON-LD `image` и `thumbnailUrl` — **относительные** URL
  (`/api/thumbnail-proxy?url=…`). Google их обычно разворачивает относительно
  страницы, поэтому это не критично, но абсолютный URL надёжнее и не вызывает
  замечаний в валидаторах. Проверьте разметку в Яндекс.Вебмастере и
  Rich Results Test после выкладки.

### 4.5. Хрупкость сборки

`getAnimeCalendar()` делает `transformAnimeCalendar(item.anime)` без проверки,
что `item.anime` существует. `/schedule` — статическая страница, поэтому один
нестандартный элемент из календаря Shikimori **валит весь `next build`**
(я на это наткнулся при отладке). Стоит добавить `if (!item?.anime) continue`.

## 5. Производительность middleware (на будущее)

На каждый запрос middleware:
1. ходит в Supabase за списком заблокированных IP (кэш 30 секунд в памяти
   инстанса — при нескольких инстансах кэш почти не помогает);
2. для `/watch/{id}` дополнительно может сходить в Shikimori.

Кэш живёт в памяти процесса, а не в общем хранилище, поэтому «холодные»
запросы случаются регулярно. Это стоит вынести в отдельный кэш (например,
в ту же Supabase с TTL или в edge-кеш).

## 7. Что сделать после выкладки

1. Переотправить `robots.txt` и `sitemap.xml` в Google Search Console и
   Яндекс.Вебмастер.
2. В Вебмастере посмотреть «Страницы в поиске» → должно резко вырасти число
   страниц `/watch` по мере обхода каталога.
3. Проверить разметку: Rich Results Test и валидатор Яндекса на 3–5 страницах
   `/watch` (в т.ч. фильм и онгоинг с серией).
4. Поднять `SITEMAP_CATALOG_PAGES`, если генерация карты сайта укладывается
   в приемлемое время (каждая страница = один запрос к Shikimori с паузой 200 мс).
5. Посмотреть в Search Console отчёт «Мягкие 404» — новые появляться не должны.
