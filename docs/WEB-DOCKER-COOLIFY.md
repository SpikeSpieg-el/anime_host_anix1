# Запасной деплой сайта через Docker (без Nixpacks)

`Dockerfile.web` в корне собирает **сайт Next.js** на Node.js 22.
Корневой `Dockerfile` по-прежнему собирает **img-сервис** на порту 3100:
его и настройки img-приложения менять не нужно.

## Переключение сайта в Coolify

Сначала доставьте файлы в ветку, которую собирает приложение сайта.
Сохраните текущие настройки Nixpacks для обратного переключения.
В приложении **сайта**, не img, укажите:

| Настройка | Значение |
| --- | --- |
| Build Pack | Dockerfile |
| Base Directory | `/` |
| Dockerfile Location | `/Dockerfile.web` |
| Build Context Directory / Location | `/` |
| Ports Exposes | `80` |
| Install / Build / Start Command | Очистить переопределения; используются инструкции Dockerfile |

Существующий домен сайта оставьте. Если в домене явно указан внутренний порт,
он должен совпадать с Ports Exposes. Удалите старое переопределение `PORT` или
задайте `PORT=80`. Другой порт тоже возможен, но тогда нужно согласовать его
с настройками прокси/Ports Exposes (EXPOSE сам по себе порт не меняет).

### Переменные окружения

- Сохраните существующие переменные сайта, включая серверные секреты, как
  **runtime**-переменные. Они не копируются в образ из `.env`: такие файлы
  исключены через `.dockerignore`.
- Используемые `NEXT_PUBLIC_*` нужно передать также как **build arguments**
  (Build Variable / Available at Buildtime в зависимости от версии Coolify).
  В Dockerfile они уже объявлены через `ARG`. Проверьте в логе, что Coolify
  действительно передаёт их как `--build-arg`.
- Особенно проверьте `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
  `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_IMAGE_SERVER_URL`, настройки PvP и Umami,
  если они используются. Сохраняйте прежние значения; не задавайте отсутствующие
  необязательные переменные пустыми без необходимости — код использует defaults.
- Next.js встраивает публичные значения в JS при сборке. После их изменения
  нужен **rebuild**, а не только restart. Для конфигурации, читаемой сервером
  (например, URL Umami и PvP в CSP), оставьте значения и в runtime.
- Не передавайте `SUPABASE_SERVICE_ROLE_KEY`, пароли БД, токены и другие
  серверные секреты через Docker ARG: это не защищённый канал хранения секретов.

Сохраните настройки и выполните Redeploy. Если ранее был включён healthcheck,
проверьте, что он обращается к порту сайта, а не img-сервиса.

## Ручная сборка

Из корня репозитория (передайте остальные используемые публичные переменные аналогично):

```sh
docker build -f Dockerfile.web -t weeb-x-web \
  --build-arg NEXT_PUBLIC_SUPABASE_URL \
  --build-arg NEXT_PUBLIC_SUPABASE_ANON_KEY \
  --build-arg NEXT_PUBLIC_SITE_URL \
  --build-arg NEXT_PUBLIC_IMAGE_SERVER_URL .

# .env.production — локальный, не коммитить; нужен для runtime-переменных.
docker run --rm --env-file .env.production -e PORT=80 -p 8080:80 weeb-x-web
```

Для `--build-arg NAME` значения берутся из экспортированных переменных shell,
а не автоматически из `.env.production`. Сайт будет на `http://localhost:8080`.
Образ запускается от непривилегированного пользователя `node`.

## Что это обходит

Здесь нет скачивания Nixpacks-образа, nixpkgs или пакетов Nix. Однако интернет
всё ещё нужен для базового образа `node:22-bookworm-slim` из Docker Hub и npm
пакетов из npm registry; возможны и запросы самого приложения во время сборки.
Если падает соединение с Docker Hub/npm, один переход на Docker это не исправит.
Для быстрого аварийного восстановления полезно заранее собрать и сохранить
проверенный образ в своём registry: тогда при сбое не потребуется новая сборка.

Вернуться на Nixpacks можно сменой Build Pack и восстановлением прежних команд;
`Dockerfile.web` не меняет работу Nixpacks или других сервисов.
