# Telegram-бот Weebx · 0.1

## Результат проверки репозитория

До 0.1 документация ссылалась на `telegram-bot/src/*`, но сам сервис в ветке
отсутствовал. Существовали таблицы привязки, API `/api/telegram/link`, страница
`/link` с переключателем уведомлений и `title_subscriptions`.
Теперь реализация находится в `telegram-bot/index.mjs`, проверка серий — `core.mjs`.

## Минимальный сценарий

1. В личном чате отправить `/start`, затем `/link`.
2. Бот выдаёт одноразовый код из 8 символов и ссылку `/link?code=...`.
3. Пользователь входит в **существующий аккаунт сайта** и подтверждает привязку.
   Бот не принимает пароли и не создаёт отдельную авторизацию сайта через Telegram.
4. `/sync` показывает, что аккаунт подключён, число подписок на серии и состояние
   Telegram-уведомлений. Подписки читаются напрямую из общей БД: переносить их
   вручную не нужно, изменения сайта видны в следующем скане.
5. При запуске и далее каждые 30 минут бот проверяет `episodes_aired` в Shikimori
   для подписок с `notify_new_episodes = true`. При росте выше baseline и последней
   доставленной в Telegram серии отправляет сообщение со ссылкой на просмотр.

Список команд: `/start`, `/link`, `/sync`. Любые старые команды и deep-link
`start=sub_...` показывают помощь, **не меняют подписки**.

## Настройки — только на сайте

- `/link`: включение/выключение Telegram-уведомлений, отвязка аккаунта.
- Страницы тайтлов: подписки и их каналы (существующий интерфейс сайта).
- Из бота нельзя включать/выключать уведомления и менять подписки.
- Колокольчик и web-push сайта остаются независимыми от Telegram.

В 0.1 нет проверки озвучек Kodik/`translation_alerts`, `/profile`, игровых
функций, ручного глобального `/scan`, управления подписками командами.
Выход серии в Shikimori **не означает**, что её русская озвучка уже доступна.

## Запуск

Нужны Node.js 22+, Postgres и созданный в BotFather бот. Из корня репозитория:

```sh
npm ci
cp telegram-bot/.env.example telegram-bot/.env
# Заполнить telegram-bot/.env (не коммитить).
node --env-file=telegram-bot/.env telegram-bot/index.mjs
```

При переменных в окружении: `npm run bot:start`.
`DATABASE_URL` — серверное привилегированное подключение с доступом к таблицам,
минуя RLS (не anon/authenticated). Рекомендуются direct connection или session
pooler. TLS настраивается строкой подключения согласно требованиям вашего Postgres;
проверку сертификатов не отключать.

Миграции применить **до запуска**:

- `20261007000000_create_telegram_bot.sql`;
- `20261008000000_create_title_subscriptions.sql` (и необходимые ей предыдущие);
- `20261115000000_telegram_episode_cursors.sql`.

Обычно применяется весь штатный набор миграций проекта, а не эти файлы отдельно.

Docker, контекст сборки — корень репозитория:

```sh
docker build -f telegram-bot/Dockerfile -t weebx-bot:0.1 .
docker run --restart unless-stopped --env-file telegram-bot/.env weebx-bot:0.1
```

Сервис работает через long polling, входящий порт не нужен. Webhook Telegram
должен быть удалён перед запуском. Запускать **одну** реплику: бот использует
блокировку в Postgres с TTL 120 секунд и продлевает её каждые 30 секунд.
Нужен исходящий доступ к `api.telegram.org`, `shikimori.one` и Postgres.

## Доставка и ограничения 0.1

- Отдельная таблица `telegram_episode_cursors` не позволяет уведомлениям сайта
  поглощать Telegram-сообщения. Первый успешный скан только записывает текущее
  число серий в курсор, без рассылки старых. Дальше курсор продвигается после
  успешной отправки Telegram.
- При пропуске нескольких серий приходит одно сообщение о последней.
- Выключенный канал пропускается; при включении может прийти последняя
  пропущенная серия. Отвязка удаляет Telegram-курсор каскадно.
- Перед отправкой повторно проверяются привязка и настройки на сайте.
- Ошибки источника/Telegram повторяются в следующем цикле; токен и коды не
  печатаются в лог. Блокировка пользователем бота не меняет настройки сайта.
- Telegram и Postgres не имеют общей транзакции: при сбое после отправки,
  но до записи курсора возможен повтор. Строгой exactly-once доставки нет.
- Скан и обработка команд последовательны; при большом числе тайтлов ответы
  на команды задерживаются. Это минимальный сервис для небольшого запуска.
- Существующий API привязки на сайте потребляет код и заменяет связь несколькими
  запросами, не одной транзакцией. При ошибке записи нужно запросить новый код;
  атомарную замену привязки стоит сделать отдельным следующим исправлением.

## Проверка работающего контейнера

1. В личном чате отправьте `/sync`. Проверьте, что аккаунт привязан,
   Telegram-уведомления включены и есть хотя бы одна подписка с каналом
   «Новые серии» на онгоинг. Ответ на команду **не подтверждает**, что скан
   или рассылка прошли успешно.
2. Откройте Logs приложения в Coolify или выполните на Docker-хосте:

   ```sh
   docker ps --format '{{.Names}} {{.Image}}'
   docker logs --since 2h ИМЯ_КОНТЕЙНЕРА
   ```

3. Актуальная сборка пишет `Episode scan complete` после каждого скана.
   `subscriptions` — число подходящих подписок, `checked` — сколько тайтлов
   успешно проверено, `seeded` — сколько подписок получили начальный курсор
   без рассылки. `sent` — сколько сообщений о сериях принял Telegram (не
   число ответов на команды). `sent: 0` без ошибок — нормальный результат,
   если новых серий нет или идёт инициализация. `invalidIds` — число
   пропущенных тайтлов с нечисловым Shikimori ID. Счётчики `sourceErrors`,
   `sendErrors`, `dbErrors` и строки перед итогом подсказывают причину сбоя.
4. Чтобы подтвердить доставку для своего аккаунта, дождитесь, пока после
   первого скана `episodes_aired` вырастет у подписанного тайтла. После
   следующей проверки убедитесь, что уведомление пришло в личный чат. Не
   правьте курсоры или baseline на production для имитации выхода серии.

Разбор частых ошибок:

| Лог | Что проверить |
| --- | --- |
| `Telegram getUpdates failed (HTTP 409)` | Другая копия бота с тем же токеном или активный webhook. Оставить один poller и отключить webhook, если этот бот должен работать через polling. |
| `Episode scan Shikimori failed` | Доступ контейнера к `shikimori.one`, HTTP-статус или сетевой код, указанный в строке. `429` — ограничение частоты, `5xx` — ошибка на стороне источника. |
| `Episode scan Telegram sendMessage failed (HTTP 403)` | Бот не может отправить сообщение в этот чат (например, пользователь заблокировал бота); остальные подписчики сканируются дальше. |
| `Database connection lost` или `ECONNRESET` при запуске | Соединение контейнера с Postgres/pooler: доступность, выбранный хост и порт, параметры TLS. Состояние Coolify `Running` не проверяет это соединение. |
| `Instance lease is still held` (в старом образе `Another bot instance is already running`) | При аварийном обрыве старая блокировка может сохраняться до 120 секунд. Если сообщение продолжается дольше, проверьте, не работает ли другая копия с той же БД. Не удаляйте блокировку вручную. |
| `Poll/scan failed; retrying` или `Failed to check/deliver anime` | Это логи старой сборки: по ним нельзя отличить причины. Пересоберите и разверните образ с актуальным кодом; простой рестарт старого образа не добавит диагностику. |

## Проверка перед релизом

```sh
npm run bot:test
node --check telegram-bot/index.mjs
```

На тестовом боте и тестовой БД проверить: `/link` → вход на сайте → подтверждение
→ `/sync`; изменение подписки на сайте → изменение счётчика `/sync`; выключение
Telegram на `/link` → отсутствие отправки; включение → отправка при росте серии;
повторный скан → без повторной отправки; отвязка → `/sync` просит привязаться.
Не менять production-baseline ради теста.

Живая проверка Telegram/Shikimori из среды разработки не выполнена: нужны
секреты окружения и разрешённый сетевой доступ. Unit-тесты проверяют формат
кода, фильтр личного чата, baseline, независимость курсора от сайта,
поведение при ошибке доставки и изменении настроек.
