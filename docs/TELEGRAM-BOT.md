# Telegram-бот Weebx

Бот пишет игроку в Telegram, когда у тайтла, который он ждёт, появилась новая
серия или озвучка. Плюс `/profile` со статистикой аккаунта.

Реализация — `telegram-bot/`, отдельный Node-сервис рядом с `pvp-server`.

---

## 1. Зачем он нужен

На сайте уже есть механизм «жду озвучку» (`translation_alerts`,
см. [EPISODE-ALERTS.md](./EPISODE-ALERTS.md)). Он работает, но с одной дырой,
которую видно только в самом механизме:

```
Гость на /watch/<id> без озвучки → «Уведомить меня» → translation_alerts
                                          │
                                          ▼
              EpisodeUpdatesProvider дёргает POST /api/alerts/check
              раз в 15 минут — ПОКА ВКЛАДКА ОТКРЫТА
```

`EpisodeUpdatesProvider` висит в `app/layout.tsx`, то есть на любой странице, но
он **клиентский**. Человек подписался на озвучку, ушёл смотреть серию на ТВ и не
заходил на сайт неделю — за это время новая серия вышла, а уведомления не будет
**никогда**. Обещание «мы напомним, когда серия появится» оказывалось
выполнимым только для тех, кто сидит на сайте с открытой вкладкой.

Бот закрывает именно эту дыру: он проверяет те же ожидания по расписанию,
независимо от того, заходил человек на сайт или нет.

## 2. Что делает

| Команда    | Что делает                                              |
| ---------- | ------------------------------------------------------- |
| `/start`   | Приветствие; показывает, привязан ли аккаунт            |
| `/link`    | Выдаёт ссылку привязки и ждёт подтверждения с сайта     |
| `/profile` | Монеты, пыль, коллекция, серия дней, крутки, бои        |
| `/alerts`  | Список отслеживаемых тайтлов + отписка от конкретного   |
| `/unlink`  | Отвязать аккаунт                                        |
| `/help`    | Справка                                                 |
| `/scan`    | Ручной запуск проверки (только владелец, нет в `/help`) |

## 3. Ключевое решение: правила не дублируются

Бот лежит в том же монорепозитории и импортирует **чистые модули сайта
напрямую**, а не их копии:

```ts
import { resolveTranslationAlert, isAlertDueForRecheck, buildAlertNotification }
  from "@/lib/translation-alerts"
import { getAnimeTranslationsResult } from "@/lib/kodik"
import { getWatchPath } from "@/lib/seo/watch-url"
import { rarityConfig } from "@/types/gacha"
```

`tsconfig.json` бота объявляет `baseUrl: ".."` — поэтому работает тот же алиас
`@/*`, которым эти файлы пользуются внутри себя.

Почему это принципиально: если бы бот держал свою копию правила «когда ожидание
считается выполненным», то сайт и бот закрывали бы одно ожидание в разный
момент и писали бы разный текст. Расхождение в правиле — это баг, который
всплыл бы через месяц, когда никто не помнит, зачем в боте этот код.

Поэтому в боте **нет** копий `translation_alerts.ts`, `kodik.ts` и `kodik-player-logic.ts`.

## 4. Привязка аккаунта

Telegram знает `telegram_id`, а ожидания лежат в БД под `user_id` из Supabase
Auth. Нужен словарь, и он по образцу активации Lampa (`lampa_device_codes`):
короткий код + TTL + статус.

```
/link в боте
   │  бот пишет telegram_link_codes (status=pending, TTL 10 мин)
   ▼
бот отдаёт ссылку https://weeb-x.com/link?code=W7KQ2M9P
   │
   ▼
человек открывает её на сайте (где залогинен) и жмёт «Привязать Telegram»
   │  POST /api/telegram/link (Bearer)
   ▼
сайт консумирует код и пишет telegram_links
   │
   ▼
бот видит telegram_links и радуется
```

### Почему код подтверждает сайт, а не бот

Код привязки — фактически временный пароль от аккаунта. Подтвердить его может
только человек, который уже вошёл в Weebx: у него есть Bearer-токен, и только он
доказывает, что аккаунт его. У бота такой проверки нет, и доверить ему код
значило бы отдать доступ любому, кто перехватил ссылку.

Бонус: консюм происходит одним `UPDATE … WHERE status = 'pending'`. Двойной клик
или две вкладки дадут 0 затронутых строк во втором случае — привязка не создастся
дважды.

### Переезд аккаунта

Привязка одна на Weebx-аккаунт и одна на Telegram-аккаунт (`UNIQUE` на оба). Если
аккаунт уже привязан к другому Telegram или наоборот, прежняя привязка удаляется.
Это осознанно: чтобы получать уведомления на новом аккаунте, нужно перепривязаться
через `/link`.

## 5. Проверка ожиданий

`src/scheduler.ts` — таймер, `src/checks/translation-alerts.ts` — разбор.

Порядок действий повторяет сайт, и он важен:

1. **строка в `episode_updates`** — колокольчик на сайте (работает на всех
   устройствах игрока). Если этот шаг упал — ожидание намеренно **не
   закрывается**, чтобы следующий скан попробовал снова. Уведомление,
   потерянное молча, — ровно тот баг, который здесь чинится.
2. **закрытие ожидания** (`notified_at`).
3. **рассылка**: web-push всем устройствам + сообщение в Telegram.

### Почему бот шлёт web-push, а не только Telegram

Пункт 2 закрывает ожидание раньше, чем это делал браузер. Закрытое ожидание
больше не попадает в выборку `notified_at IS NULL`, поэтому клиентский чек его не
увидит и push не отправит.

Без рассылки из бота люди **без привязки к Telegram потеряли бы уведомление
целиком** — тише, чем было. Поэтому бот дублирует web-push на тех же условиях,
что и сайт: тот же VAPID, та же таблица `push_subscriptions`, те же мёртвые
подписки (410/404) вычищаются.

### Троттлинги и лимиты

| Ограничение                     | Значение                              | Откуда взялось                                    |
| ------------------------------- | ------------------------------------- | ------------------------------------------------- |
| Повторная проверка одного ожидания | 30 минут                            | `ALERT_MIN_RECHECK_INTERVAL_MS`, как на сайте      |
| TTL кэша списка озвучек          | 10 минут                              | `ALERT_TRANSLATIONS_TTL_MS`                       |
| Интервал скана                  | 20 минут (`ALERTS_SCAN_INTERVAL_MS`)  | Сознательно медленно: озвучки не появляются каждые 15 минут |
| Ожиданий за скан                 | 80 (`ALERTS_BATCH_SIZE`)               | Защита от таймаута по Kodik                        |
| Параллельных запросов к Kodik   | 3                                      | Как на сайте                                     |
| Сообщений в секунду в Telegram   | 25                                     | Лимит Telegram ~30/сек на аккаунт                  |

### Сбой Kodik ≠ «озвучки нет»

`getAnimeTranslationsResult` возвращает `{ translations, ok }`. При `ok = false`
бот **не ставит** `last_checked_at`: иначе окно сбоя заблокировало бы проверку на
полчаса, и «озвучки нет» выглядело бы «озвучки нет» ещё долго после
восстановления. Сбой Kodik также **не кэшируется** — иначе одно окно сбоя
заблокировало бы проверки на 10 минут.

### Один тайтл — один запрос Kodik

Часто один тайтл ждут несколько человек. Бот группирует ожидания по
`anime_id` и спрашивает Kodik один раз, а разбирает все ожидания по кэшу.

Shikimori (`episodes`) тоже запрашивается **один раз на скан**, а не по разу на
каждый закрытый тайтл — только чтобы в тексте было «вышла 5 серия из 12».

## 6. Чего бот не делает

**Не трогает экономику.** Балансы лежат в `user_coins` / `user_dust` и пишутся
только через RPC `economy_spend` / `economy_claim_daily`, которые проверяют
серверные инварианты (лимиты, потолок PvE, инвариант EV крутки). Прямой `UPDATE`
из бота обошёл бы все эти проверки, поэтому `/profile` только **читает**.

По той же причине в боте нет гачи, покупок и рынка: всё, что двигает экономику,
остаётся в интерфейсе сайта.

Не делает бот и `/unlink` разрушительным: отвязка стирает только строку в
`telegram_links`. Ожидания в `translation_alerts` принадлежат аккаунту на сайте
и после повторной привязки продолжают отслеживаться.

## 7. Установка

```bash
cd telegram-bot
cp .env.example .env     # токен от @BotFather + ADMIN_TELEGRAM_ID
npm install
```

`SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `KODIK_API_TOKEN` и `VAPID_*` берутся из
корневого `.env` сайта автоматически: `src/config.ts` читает сначала
`telegram-bot/.env`, потом корневые `.env` / `.env.local`, и уже установленное
не перезаписывает.

Миграция — **до** деплоя сайта и бота:

```bash
psql "$DATABASE_URL" -f supabase/migrations/20261007000000_create_telegram_bot.sql
```

Без таблиц бот поднимется и будет отвечать на команды, но не найдёт привязок и не
разберёт ни одного ожидания (в этом случае он честно напишет об ошибке в лог).

### Если бот падает с `ReferenceError: Headers is not defined`

Значит процесс стартовал на Node ниже 18. npm добавляет в PATH `bin`-директории
**всех** `node_modules` выше текущего каталога, поэтому один посторонний пакет
`node` в домашней папке перебивает nvm-версию и ломает все npm-скрипты проекта
целиком, а не только бота. Проверка и обход — в
[`telegram-bot/README.md`](../telegram-bot/README.md).

## 8. Деплой

Бот — отдельный сервис, как `pvp-server`. Схема развёртывания и Dockerfile
появятся вместе с выкаткой; сейчас бот рассчитан на локальный запуск.

Если деплой в Coolify, понадобится:

| Переменная          | Обязательна | Комментарий                                  |
| ------------------- | ----------- | -------------------------------------------- |
| `TELEGRAM_BOT_TOKEN` | да         | Токен @BotFather                             |
| `SUPABASE_URL`      | да         | Или из общего `.env`                         |
| `SUPABASE_SERVICE_KEY` | да      | `service_role`, иначе бот не увидит ожиданий |
| `KODIK_API_TOKEN`   | для уведомлений | Иначе сканы работать не будут            |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | для web-push | Иначе уйдут только те, кто привязал Telegram |
| `ADMIN_TELEGRAM_ID` | нет        | Без него бот не шлёт отчёты                 |
| `SITE_URL`          | нет        | По умолчанию `https://weeb-x.com`            |

Long polling, а не webhook: сервису не нужно пробивать себе публичный HTTPS с
валидным сертификатом. Плата — нельзя запускать две реплики (вторая получит
ошибку от Telegram при старте, что, в общем, удобный способ не заметить дубль).

## 9. Диагностика

Ручной прогон без ожидания двадцати минут:

```
/scan
```
(доступно только `ADMIN_TELEGRAM_ID`; команда не показывается в `/help`)

Кто привязан:

```sql
select telegram_id, telegram_username, linked_at, last_notification_at
from public.telegram_links
order by linked_at desc;
```

Что сейчас ждут:

```sql
select anime_id, anime_title, episode, baseline_episode,
       last_checked_at, notified_at, created_at
from public.translation_alerts
where notified_at is null
order by last_checked_at asc nulls first;
```

Сколько ожиданий закрылось уведомлениями:

```sql
select count(*) filter (where notified_at is not null) as delivered,
       count(*) filter (where notified_at is null)     as waiting
from public.translation_alerts;
```

Чистка протухших кодов (в боте планировщик делает это сам):

```sql
select cleanup_telegram_link_codes();
```

## 10. Известные ограничения

* **Новые серии у онгоингов не отслеживаются.** Бот работает с `translation_alerts`
  («жду озвучку по конкретному тайтлу»). Механизм `episode_updates` для онгоингов
  живёт в браузере и строится из `watch_history ∪ bookmarks` — чтобы перенести
  его на сервер, нужна отдельная работа со списком тайтлов.
* **Коды привязки живут 10 минут.** Страница привязки — один экран; если человек
  отвлёкся, придётся нажать `/link` ещё раз.
* **Второй аккаунт на одном Telegram нельзя привязать**, не отвязав первый.
* Уведомления приходят только в личные чаты: `chat_id` хранится явно, но групп
  и каналов бот не обслуживает.
