# Аудит от 05.11.2026: что исправлено и как это проверить

Дата: 2026-11-06. Речь о пунктах P0 из внешнего аудита (TTFB, H1, `no-store`,
www, утечка в robots.txt). Ниже — по каждому пункту: причина, правка, способ
проверки. Живые замеры продакшена после деплоя нужно перепроверить снаружи.

## 1. www не работал (TLS)

См. `docs/WWW-REDIRECT.md`: middleware отдаёт 308 на apex, но **на сервере
нужно добавить `www.weeb-x.com` в site-адреса Caddy**, иначе TLS-рукопожатие
падает до приложения. Это единственный пункт из списка, который нельзя
закрыть кодом.

## 2. Главная отдавала пустой HTML

Это оказалось серьёзнее, чем «нет H1».

**Причина.** В `HomePageClient` вызывался `useSearchParams()` (пасхалки из
URL). Во время серверного рендера такой вызов заставляет React выбросить
поддерево до ближайшей Suspense-границы (`BAILOUT_TO_CLIENT_SIDE_RENDERING`),
а граница была с `fallback={null}` — то есть в HTML не попадало НИЧЕГО:
ни «Ленты обновлений», ни новостей, ни ссылок на `/watch`. Плюс отдельный
`if (!isLoaded) return <спиннер>` в `useTVMode` и `isLoaded=false` в
`HeroBanner` не давали отрисоваться и первому экрану.

**Правка.**
- логика пасхалок вынесена в `components/home/home-easter-eggs.tsx` со своей
  Suspense-границей: bailout теперь касается только пустого компонента;
- `Suspense` вокруг `HomePageClient` получил серверный фолбэк
  (`HomePageClientSkeleton`), а не `null`;
- `HeroBanner` стартует с `isLoaded=true`: заголовок, метаданные, кнопки и
  обложка попадают в HTML сразу.

**Проверка (локальная прод-сборка):**

```sh
npm run build && npx next start -p 3000
curl -s localhost:3000/ | grep -c 'href="/watch/'        # было 0, стало >0
curl -s localhost:3000/ | grep -o '<h1' | wc -l          # 1
```
Замер на сборке с тестовыми данными: 11 → 17 ссылок на `/watch`, 1 → 9 `<h2>`,
HTML 118 КБ → 260 КБ при живом контенте.

## 3. `/catalog`, `/genre/*`, `/watch/*` отдавались с `private, no-store`

**Причина.** `cookies()` в `app/catalog/page.tsx`, `app/genre/page.tsx` и
`app/genre/[slug]/page.tsx` (чтение `allow_nsfw_search`) плюс `cache:
'no-store'` у обзора редакции на `/watch`. Любое из этого помечает маршрут
динамическим: ни ISR, ни CDN-кэш не работают, каждый хит рендерится заново.

**Правка.**
- NSFW-настройка больше не читается на сервере: серверные версии каталога и
  жанров всегда «безопасные» (как у гостя и краулера). Пользователю с
  включённым NSFW список догружает клиент (в `CatalogClient` уже был этот
  путь через `profile.allow_nsfw_search`);
- `/genre/[slug]` → `revalidate = 600`, `/genre` → `revalidate = 3600`;
- обзор редакции кэшируется (`next: { revalidate: 300, tags: […] }`) и
  дедуплицируется через React `cache()`; админка после сохранения вызывает
  `revalidateTag`/`revalidatePath`, поэтому правка видна сразу.

**Проверка:**
```sh
for u in /catalog /genre/ekshen /schedule /news; do
  curl -sI "localhost:3000$u" | grep -i cache-control
done
```
`/catalog` остаётся `no-store` (страница зависит от `searchParams`, это
осознанно), `/genre/*` — `s-maxage`.

## 4. `/watch`: TTFB 1,9–2,9 с

**Причины (по коду, а не по догадкам):**
1. `await getAnimeFranchise()` стоял в теле страницы — на «Ван-Писе» это 30+
   последовательных запросов к Shikimori (внутри `shikimoriJson` пауза 200 мс
   между запросами) **до** первого байта HTML;
2. `permanentRedirect` «страховки канонического slug» выполнялся на каждом
   заходе;
3. обзор редакции тянулся дважды (metadata + страница) и всегда мимо кэша;
4. `transformAnime` для `/watch` перебирал AniList → Kitsu → Kodik → MAL за
   обложкой, если Shikimori-постер не проходил проверку — последовательно.

**Правка:**
1. франшиза ушла в `<Suspense>` (`WatchPageWithWatchOrder`): блок «порядок
   просмотра» стримится, первый байт его не ждёт. Узлы франшизы теперь
   запрашиваются параллельно;
2. редирект-страховка стала клиентским `<CanonicalSlugGuard/>`;
3. обзор кэшируется и дедуплицируется (см. п.3);
4. `/watch` берёт обложку только у Shikimori (`allowExternalPosters: false`),
   фолбэк — сгенерированная заглушка вместо трёх внешних кругов;
5. в `lib/shikimori/client.ts` добавлены дедупликация одновременных запросов
   и stale-while-revalidate (протухшая запись отдаётся сразу, обновляется
   фоном), TTL по умолчанию поднят с 30 с до 5 мин;
6. `resolveBestPoster` проверяет источники обложек параллельно
   (`Promise.allSettled`) и дедуплицирует одновременные вызовы для одного
   тайтла — это и был вклад в «холодный старт главной» в 8,9 с;
7. POST-запросы к Kodik API получили `next: { revalidate }` — раньше они
   кэшировались в Next бесконечно, теперь 6 часов.

## 6. Прочее из того же аудита

- `robots.txt` вычищен от внутренних подробностей (схема токенов, путь к
  исходнику плеера, история «страйков»). Правила обхода не изменились,
  объяснения переехали в `docs/ROBOTS-SITEMAP.md`;
- `nhost.weebx.duckdns.org:8443` убран из CSP (и в `middleware.ts`, и в
  `next.config.mjs`);
- HSTS: добавлен `includeSubDomains`; `preload` намеренно нет;
- hero-обложка главной: `priority` (eager + preload + high) вместо `lazy`;
- на `/watch` добавлен `<link rel="preload" as="image">` для постера плеера.

## Что осталось за пределами этой правки

Это требует доступа к серверу/CDN и не решается в репозитории:

1. **Caddy**: добавить `www.weeb-x.com` в site-адреса и `encode zstd br gzip`;
2. **Cloudflare proxy** (сейчас DNS-only): edge-кэш статики, сокрытие origin,
   защита от L7;
3. **CSS 512 КБ** — нужен отдельный аудит purge/split в Tailwind-конфиге;
4. **`og:image`** для `/privacy`, `/contacts`, уникальный title `/easter-eggs`;
5. `srcset w=3840` → фактические размеры (правится в `sizes` у конкретных
   карточек);
6. Яндекс.Метрика и Goals в Umami — продуктовая задача, не техническая.
